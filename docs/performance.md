# Производительность индексации

Замеры от 2026-09-19. Устройство: Snapdragon 8s Gen 3 (SM8635: 1×X4 + 4×A720 + 3×A520),
Android 16, ONNX Runtime 1.30 (CPU EP), медиатека ~6300 файлов.

## Итог

| Этап оптимизации | Время на файл (среднее) |
|---|---|
| Исходно: CLIP + ViT NSFW на каждом кадре | ~800 мс |
| Гибридный NSFW: LAION-префильтр поверх CLIP, ViT только на ~10% кадров | ~195–246 мс |
| + конвейер «подготовка ‖ инференс» | **~140 мс** (55–90 мс в окнах без ViT) |

Медиатека ~6000 файлов индексируется примерно за 15 минут (было ~1,5 часа).

## Разбивка по этапам (текущая версия, окно из 64 файлов)

| Этап | Среднее | Примечание |
|---|---|---|
| `clip.run` | 44–50 мс | CLIP ViT-B/32 int8 |
| `nsfw.run` | 500–700 мс | ViT NSFW 384×384 int8, только ~10% кадров → 50–70 мс на файл в среднем |
| `nsfw.clip` | 0,3 мс | LAION MLP поверх CLIP-эмбеддинга |
| `prepare.total` | 32–50 мс | декодирование превью + dHash + тензор CLIP; **идёт параллельно** с инференсом |
| БД (чтение страницы, upsert) | <1 мс на файл | |

Как снять: `adb logcat -s IndexPerf` — воркер печатает сводку каждые 64 файла (`perf/PerfStats.kt`).

## Микробенчмарк ONNX-моделей

Приложение на экране (cpuset `top-app`), телефон остывший (thermal headroom 0,40–0,48),
медиана на кадр.

**CLIP ViT-B/32 (224×224)**

| Вариант | Результат |
|---|---|
| int8, CPU, 2 / 3 / 4 / 5 / 6 потоков | 32,5 / 29,2 / 30,4 / 34,7 / 28,4 мс |
| int8, CPU, 8 потоков | 59,2 мс — малые ядра тормозят весь слой |
| int8, XNNPACK, 4 потока | 49,8 мс |
| fp16 / q4, CPU, 4 потока | 86,7 / 92,9 мс |
| int8, батч 4 / батч 8 | **21,3** / 32,4 мс на кадр |

**ViT NSFW (384×384)**

| Вариант | Результат |
|---|---|
| int8, CPU, 3 / 4 / 5 / 6 потоков | ~460 / ~410–460 / ~290–550 / ~300–420 мс (шум DVFS больше разницы) |
| q4 / fp16 / fp32, 4 потока | 973 / 1239 / 1251 мс |

Выводы: int8 на CPU — лучший вариант для обеих моделей; XNNPACK, fp16 и q4 медленнее;
число потоков 3–6 не влияет заметно (оставлено 4). Батч 4 для CLIP даёт −30% — не внедрено.

## NPU (Hexagon) — недоступен, проверено 2026-09-23

Poco F6 (Snapdragon 8s Gen 3, SM8635) — NPU в чипе есть (в `dumpsys thermalservice` видны
датчики `nsp0..nsp3`), но обычному приложению он не достаётся ни одним из двух путей:

- **NNAPI.** В системе нет HAL `android.hardware.neuralnetworks` (`lshal`, `service list` —
  пусто), драйвер производителя не поставлен: NNAPI объявлен устаревшим в Android 15.
  Провайдер `nnapi` с флагом `CPU_DISABLED` берёт **0 узлов из 1026**, всё уходит на CPU.
- **QNN (прямой доступ к Hexagon).** `onnxruntime-android-qnn` не создаёт устройство:
  `QNN SetupBackend failed ... QNN_DEVICE_ERROR_INVALID_CONFIG`. Причина — FastRPC закрыт:
  `/dev/adsprpc-smd` принадлежит `system:system` с правами `crw-rw-r--`, `/dev/cdsprpc-smd`
  (узел для приложений) отсутствует, библиотек QNN в `/vendor/lib64` и `/odm/lib64` нет.
  Бэкенд QNN GPU отвечает `QNN_COMMON_ERROR_PLATFORM_NOT_SUPPORTED`.
  Сборка `-qnn` вдобавок собрана без NNAPI, то есть заменяет его, а не дополняет.

Статическая QDQ-модель (то, что требуется ускорителям) собрана и замерена — без NPU она
только вредит:

| CLIP ViT-B/32, 224×224, 6 потоков | на экране (`top-app`) | фоновые ядра |
|---|---|---|
| динамическая int8 (в приложении) | **29,6 / 34,3 мс** | 366–533 мс |
| статическая QDQ int8 | 70,4 / 87,5 мс | 423–448 мс |

Точность статической модели тоже хуже (косинус к fp32 на 30 снимках): min/max 0,764,
процентиль 99,99 — 0,408, процентиль 99,999 — 0,808, энтропия 0,764, тогда как у текущей
динамической int8 — 0,937. Спасают только 16-битные активации (0,997), но это 385–439 мс
на кадр. Причина классическая для ViT: выбросы в активациях после LayerNorm не влезают
в 8-битную шкалу, а выбор метода калибровки этого не лечит.

### GPU через OpenCL — доступен, но выигрыш невелик

В отличие от NPU, GPU приложению открыт: `/vendor/lib64/libOpenCL.so` есть в
`/vendor/etc/public.libraries.txt` (то есть приложение имеет право его загрузить),
`/dev/kgsl-3d0` — `crw-rw-rw-`. Проверено отдельной программой на NDK (`dlopen` +
перечисление устройств): платформа QUALCOMM Snapdragon, **OpenCL 3.0**, устройство
Adreno 735, есть `cl_khr_fp16`, целочисленные dot-product и SVM.

Замер умножения матриц 1024×1024×1024 на этом GPU:

| Ядро | Время | Пропускная способность |
|---|---|---|
| fp32, плитка 4×4, векторные чтения | 10,7–11,1 мс | 193–201 GFLOPS |
| fp16, то же | 9,4–9,7 мс | 221–229 GFLOPS |
| fp16 с тайлингом через локальную память | 15,2 мс | 141 GFLOPS — Adreno это не любит |

Для сравнения: CLIP ViT-B/32 — около 8,8 GFLOP на кадр, у нас 30 мс на CPU, то есть
конвейер int8 на больших ядрах даёт эквивалент ~290 GOPS. Даже вылизанное ядро на GPU
(с чтением через image2d, как в делегате LiteRT) дало бы в лучшем случае полтора-два раза,
а ORT для Android вовсе не умеет OpenCL — понадобился бы второй рантайм (LiteRT/MNN) и
конвертация моделей. Отдельный минус: GPU делится с отрисовкой интерфейса.

**Энергия.** Датчик тока приложению закрыт, профиля питания на устройстве нет, поэтому
сравнивали по нагреву (он пропорционален потраченной мощности): 90 секунд нагрузки с
одинаковой стартовой температуры корпуса (~48 °C).

| Нагрузка | Сделано за 90 с | Кристалл до → после |
|---|---|---|
| GPU, fp16-умножения | 22,6 TFLOP (250 GFLOPS) | GPU 52,6 → 76,3 °C, CPU 60,5 → 78,2 °C |
| CPU, CLIP int8 (1500 кадров) | 13,2 TFLOP-эквивалента (147 GOPS) | CPU 70,3 → **56,5 °C** (остыл под нагрузкой) |

То есть GPU даёт примерно в 1,7 раза больше операций в секунду, но греется так, что
кристалл за полторы минуты прибавляет больше 20 °C, тогда как четыре потока int8 на
процессоре телефон даже не удерживают от остывания. Оговорка: наше ядро берёт лишь ~20%
от пика GPU и много ходит в память, вылизанное было бы экономнее — но и int8 на CPU
использует инструкции скалярного произведения, которых в OpenCL-ядре нет.

Единственный довод за GPU — не скорость сама по себе, а параллелизм: пока эмбеддинги
считает GPU, процессор свободен для превью, хешей и базы. Инференс занимает ~95–120 мс
из ~140 мс на файл, так что полная разгрузка процессора упёрлась бы в подготовку кадра
(~40 мс) — потолок выигрыша около двух раз.

Вывод: направление закрыто на этом устройстве. Скрипты квантования лежат в истории задачи;
возвращаться к ним имеет смысл только на телефоне с работающим NNAPI-драйвером или с
доступным FastRPC. Реальный резерв скорости — не NPU, а более лёгкая модель (уровня
MobileCLIP) и правильные ядра: разница `top-app` против фоновых ядер — десятикратная,
больше любой оптимизации модели.

## Темп индексации: полный и тихий

`work/IndexingPace.kt` решает, на что индексация имеет право прямо сейчас.

| Режим | Когда | Потоки | Паузы |
|---|---|---|---|
| Полный | зарядка + система считает устройство простаивающим (ночь), либо приложение открыто на экране | 4 | только тепловые |
| Тихий | всё остальное: батарея, телефон в руках, фоновые запуски | 2 | после каждого кадра, занимаем ~25% времени |

Тихий проход ограничен окном в 10 минут: отработав его, воркер уходит с `Result.retry()`,
а остаток медиатеки ждёт ночи. Без этого дневная индексация за несколько часов съедает
суточный лимит foreground-сервиса — и ночью его уже не будет.

Ночной проход ставится отдельной задачей `media-index-night` с условиями «зарядка +
device idle»: система сама запустит её, когда телефон отложат на зарядку. Оба прохода —
один и тот же воркер, поэтому вдвоём они не идут (флаг `running`).

Число потоков задаётся при загрузке моделей, то есть в начале этапа: если темп сменился
посреди этапа, до конца этапа меняются только паузы. «Приложение на экране» берётся из
`SpaceGalleryApp.isOnScreen` — по важности процесса судить нельзя, она становится
«сервисной», как только воркер поднимает foreground service.

Проверено на устройстве (2026-09-23, лог `IndexPerf`): с приложением на экране
`pace=FULL importance=100`, после сворачивания — `pace=QUIET importance=125`, скорость
падает с ~140 до ~300–430 мс на файл, то есть примерно вчетверо, как и задумано.

**Тепловой предохранитель** работает в обоих режимах: при `getThermalHeadroom` выше 0,85
воркер ждёт, пока не станет 0,7. Это не бережливость ради бережливости — на перегретом
телефоне кадр стоит 83 мс вместо 36 (см. замеры ниже), то есть счёт без остановки в какой-то
момент начинает жечь батарею впустую.

Переключатель «Тихая индексация» в настройках заставляет всегда работать тихо.

## Особенности замеров на устройстве

- **Нагрев.** После нескольких минут непрерывной нагрузки ядра доходят до 90–95 °C, скорость
  падает в разы. Бенчмарк ждёт остывания (`PowerManager.getThermalHeadroom`) перед каждой
  конфигурацией. `getThermalHeadroom` возвращает NaN при вызове чаще раза в секунду.
- **cpuset.** Процесс без экрана и без foreground service попадает в cpuset `background` —
  только ядра 0–2 (A520): модели в ~4 раза медленнее. Foreground service → `foreground` (все ядра),
  приложение на экране → `top-app` (все ядра + буст планировщика; инференс ещё в ~1,5 раза быстрее).
  Проверка: `adb shell cat /proc/$(adb shell pidof ai.recommend.spacegallery)/cpuset`.
- **WorkManager хранит задачи** между force-stop и переустановкой: забытые прогоны бенчмарка
  выполняются параллельно и искажают результаты.
- **`adb logcat -c`** на этом устройстве не очищает буфер — ориентироваться на уникальные маркеры.

## Лица и люди (2026-09-20, медиатека ~15 000 фото, 13 100 лиц)

**Модель распознавания.** Замер на 448 лицах с разметкой пользователя (положительные пары —
подтверждённые лица одного человека, отрицательные — лица с одного снимка). Порог берётся так,
чтобы отсечь 99% пар «разные люди»; смотрим, сколько при этом теряется пар «тот же человек»:

| Модель | Потеря своих | AUC | Размер | Скорость |
|---|---|---|---|---|
| SFace 128-d (было) | 7% | 0.9959 | 39 МБ | 41 мс |
| MobileFaceNet (buffalo_s) | 5% | 0.9966 | 13,6 МБ | 24 мс |
| ArcFace r50 (buffalo_l) | **1%** | **0.9989** | 174 МБ | 231 мс |

Выбор модели вынесен в настройки: по умолчанию быстрая, точная — по желанию (её файл
скачивается отдельной группой). Смена модели не требует повторного поиска лиц: в базе хранятся
ключевые точки, и вектор пересчитывается по ним (~0,6 с на лицо вместе с декодированием кадра).

**Первый экспорт ArcFace из зеркала дал результат хуже SFace** (AUC 0.949) — это была неверная
предобработка, а не слабость модели: insightface ждёт RGB и (x − 127.5) / 127.5.

**Группировка.** Прежний вариант кластеризовал только 3000 самых чётких лиц, остальные
«прилипали» к готовым группам по строгому порогу. На 12 251 лице это давало 874 нарушения
пользовательских отметок «это не он»; кластеризация всех лиц — 26. Сейчас используется средняя
связь на разреженном графе соседей: сходство групп считается точно через суммы векторов,
кандидаты ищутся по случайной проекции в 64 измерения.

Пересборка людей на 13 129 лицах (512-мерные векторы): **75 с**, из них поиск соседей 15,7 с,
слияния 7,7 с, остальное — чтение лиц, обложки и запись.

**Грабли, найденные замерами:**
- копия модели из assets кешировалась навсегда — после замены файла приложение продолжало
  считать старой моделью (теперь копия обновляется по размеру файла);
- ArcFace (174 МБ) + детектор + две модели CLIP не помещались в память, процесс убивала
  система: проверка «лицо ли это» вынесена в отдельный этап после освобождения моделей лиц;
- 13 тысяч строк с 512-мерными векторами не влезают в окно курсора — выборка идёт страницами;
- список людей тянул аватары всех ~900 человек разом и падал так же: теперь аватар грузится
  для видимых строк.

### Быстрая модель против точной (2026-09-20)

На одних и тех же 2997 подтверждённых лицах 59 человек (цепочка одинаковая: кроп из оригинала
с повторным поиском точек):

| Модель | AUC | Порог | Полнота | Склейки разных людей | Кусков на человека |
|---|---|---|---|---|---|
| MobileFaceNet (быстрая) | 0.991 | 0.25 | 0.93 | 32 | 2 |
| ArcFace r50 (точная) | 0.997 | 0.30 | 0.96 | 33 | 1 |

Радиус группировки у быстрой модели поэтому свой — 0.75 (сходство 0.25): её прежнее значение
0.65 теряло треть пар одного человека. Векторы моделей несравнимы, у каждой своя шкала.

### Разрешение кропа лица (2026-09-20)

Лица ищутся на превью 640 px, и там медианное лицо занимает **22–29 px**. Вектор такого лица
совпадает с вектором того же лица из оригинала лишь на 0.73–0.87 — на уровне, где модель видит
разных людей.

Замер на 1252 лицах (снимки с камеры, ≥1600 px; ошибка — склейка лиц с одного снимка, польза —
доля лиц, попавших в группы; пороги подобраны так, чтобы ошибок было поровну):

| Ошибок | Превью 640 | Кроп из оригинала | Кроп + повторный поиск точек |
|---|---|---|---|
| ~13 | 61% | 65% | **69%** |
| ~11 | 53% | 60% | **64%** |
| ~9 | ~47% | 52% | **59%** |

Сам по себе кроп почти не помогает: ключевые точки, снятые на 29-пиксельном лице, слишком
грубы, и выравнивание съедает выигрыш. Точки нужно искать заново уже внутри вырезанного куска —
тогда при той же ошибке в группы попадает на 8–12 процентных пунктов больше лиц.

Лаборатория для таких замеров лежит в `tools/facelab/`: та же цепочка (YuNet -> выравнивание ->
ArcFace) на onnxruntime для Python, работает с файлами на диске в 10 раз быстрее телефона.

## Бенчмарк (только debug-сборка)

Код: `app/src/debug/java/ai/recommend/spacegallery/bench/`. Модели кладутся во внутреннее
хранилище приложения (файлы, залитые adb в `Android/data`, приложению не читаются):

```bash
adb exec-in run-as ai.recommend.spacegallery sh -c 'mkdir -p files/bench && cat > files/bench/clip_int8_224.onnx' < vision_model_quantized.onnx
# суффикс _NNN в имени задаёт размер входной картинки (по умолчанию 224)

adb shell am broadcast -n ai.recommend.spacegallery/.bench.BenchmarkReceiver \
  --es run r1 --es models "clip_int8_224.onnx" --es threads "2,4" --es eps "cpu,xnnpack" \
  --es batches "1,4" --ei iters 30
adb logcat -s OrtBench            # прогон заканчивается строкой "=== done r1"

# отменить все прогоны / переиндексировать всю медиатеку
adb shell am broadcast -n ai.recommend.spacegallery/.bench.BenchmarkReceiver --es action cancel
adb shell am broadcast -n ai.recommend.spacegallery/.bench.BenchmarkReceiver --es action reindex
```

Приложение на время замеров должно быть на экране (`adb shell svc power stayon usb`),
иначе результаты отражают фоновые ядра.

## Дальнейшие возможности

1. ViT NSFW — основная оставшаяся статья (~50–70 мс на файл). NPU отпадает (см. выше),
   остаётся замена на более лёгкую модель или прореживание кадров.
2. Батч 4 для CLIP: около −9 мс на файл.
3. Паузы по thermal headroom при долгой индексации — стабильная скорость и холодный телефон.
